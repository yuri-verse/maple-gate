랭킹 트래픽 조사 프로토콜

본인 PC 클라이언트가 정상적으로 전투력 랭킹을 표시할 때 오가는 네트워크 요청을 관찰해, 스크린샷 제출 없이 랭킹을 수집할 수 있는지 판단하기 위한 절차서입니다. 수집 코드는 아직 쓰지 않습니다 — 먼저 무엇이 가능한지부터 확정합니다.

본인 PC 클라이언트 본인 계정 · 본인이 보는 화면 인증서 고정 우회 없음 암호화 · 인증 · 보안 우회 없음

이미 확인된 사실

클라이언트 파일 · 공개 CDN 에서 확인 (우회 아님)

게임은 지역별 HTTPS 서비스 호스트와 통신합니다. 공개 서버 설정 파일(host_live_windows.json)에 그대로 적혀 있습니다.

서버지역호스트
스카니아KRmakr-service.nexon.com
루나EUmaeu-service.nexon.com
베라NAmana-service.nexon.com
아리아TWmatw-service.nexon.com
아퀼라SGmasg-service.nexon.com

TLS 인증서는 표준 DigiCert 발급 *.nexon.com — OS 신뢰 저장소를 쓴다는 뜻이라, 앱 레벨 고정만 없으면 프록시 캡처가 통할 여지가 있습니다. 알 수 없는 경로에는 404 를 돌려주는 RPC 형태 서비스라, 실제 랭킹 요청 경로·본문 형식은 서버가 알려주지 않습니다 — 그래서 본인 클라이언트 트래픽을 봐야 합니다. 엔진은 Unity(빌드 1.14.0)입니다.

이 게임이 맞나 — 클라이언트 제품명은 MapleIdleRPG, CDN 경로는 com.nexon.ma(Maple Adventure = 메이플키우기 내부코드). 서버 이름(스카니아·루나…)은 원조 메이플스토리에서 가져다 쓴 것이라 겹쳐 보이지만, 위 호스트는 모두 메이플키우기 서버입니다.

정적 분석으로 더 확인됨 (2026-08-27) — 클라이언트 로컬라이제이션에 랭킹 데이터 모델이 그대로 들어 있습니다: ENUM.RANKINGTYPE.BATTLEPOWER(전투력 랭킹), RANKINGFILTERTYPE.ALL / CURRENTRANKING(필터), CURSOR(커서 페이징), ERRORTYPE.ALLOCATIONWORLDIDFAILED(worldId 관련). 즉 rankingType · worldId(전체/서버별) · cursor 형태의 요청이 실재합니다. 서버는 Kestrel · HTTP/2(ASP.NET Core, gRPC 계열로 추정), 인증은 넥슨 플랫폼(NP) 로그인. 다만 실제 요청 경로 · 메시지 스키마 · 서명 유무는 GameAssembly.dll/global-metadata.dat 를 받아 분석했습니다. 결과: 호출은 C1Shared.GetBattlePowerRankingList(cursor·filterType·worldId·creatureIndex), 전송은 NXP 네트워크 클라이언트(MemoryPack), 그리고 요청마다 세션키+롤링 nonce 서명 + GSSDK 무결성 검사. 아래 4번 결론 참조.

1

사용할 캡처 도구

TLS 본문을 읽으려면 내 PC 에서 내 트래픽을 복호화한다 — 서버 보안을 뚫는 게 아니다

전송 형태를 먼저 파악한 뒤(HTTPS 인지, QUIC/UDP 인지, 원시 TCP 인지) 도구를 고릅니다. 순서대로 시도하고, 첫 번째로 통하는 것에서 멈춥니다.

Wireshark전송 파악Windows

가장 먼저. 랭킹 화면을 여는 순간 어느 호스트·포트로, 어떤 프로토콜이 나가는지 본다 — TCP 443(TLS) 인지, UDP 443(QUIC) 인지, HTTP/2 인지. 본문은 못 읽지만 이 한 번으로 뒤 도구가 정해진다.

SSLKEYLOGFILE + Wireshark1순위 시도환경변수

클라이언트의 HTTP 스택이 SSLKEYLOGFILE 환경변수를 존중하면, 그 파일에 세션 키가 적히고 Wireshark 가 그 키로 본문을 복호화한다. 클라이언트가 스스로 키를 내주는 방식이라 프록시도 CA 설치도 필요 없고 — 인증서 고정과도 무관하다. 가장 깨끗한 길. 되면 여기서 끝.

mitmproxy2순위 시도무료 · 스크립트

SSLKEYLOGFILE 이 안 통하면 시스템 프록시로 트래픽을 돌리고, mitmproxy 의 CA 인증서를 내 Windows 신뢰 저장소에 넣는다. 이건 내 기기에서 내 트래픽을 들여다보는 표준 디버깅이지 서버 우회가 아니다. mitmweb 로 요청을 눈으로 보고, 필터를 ~d *-service.nexon.com 로 건다.

대안(같은 원리): Fiddler Classic, Charles, Proxyman — 취향대로.

여기서 갈린다. mitmproxy CA 를 넣었는데 클라이언트가 접속에 실패하거나 네트워크 오류를 뱉으면 → 인증서 고정(pinning)이 걸려 있는 것이다. 그 선을 넘는 방법은 고정 우회뿐이고, 그건 이 조사의 범위 밖이다. 아래 P3 관문에서 판정한다.

2

구체적인 확인 순서

각 단계는 실제 순서다 — 앞 단계 결과가 다음 도구·판단을 정한다

사전 준비

깨끗한 캡처 환경을 만든다. 다른 앱은 닫아 잡음을 줄이고, 게임 빌드 번호를 적어 둔다 (패치되면 요청 형식이 바뀔 수 있다).

산출 — 캡처 환경 · 게임 버전 기록

전송 형태 파악 (Wireshark)

게임 실행 → 로그인 → 랭킹 화면 진입. 캡처에서 ma*-service.nexon.com 으로 가는 흐름을 찾아 다음을 확정한다:

  • TCP 443 (TLS) 인가, UDP 443 (QUIC) 인가, 원시 TCP 인가
  • HTTP/1.1 인가 HTTP/2 인가 (TLS ALPN 값)
  • 랭킹 진입 시점에 실제로 새 요청이 나가는가
산출 — 전송 프로토콜 확정 → 캡처 도구 선택

복호화 관문 — 여기서 가능/불가가 갈린다

SSLKEYLOGFILE 을 먼저, 안 되면 mitmproxy + CA 를 시도. 클라이언트가 평소처럼 붙고 랭킹이 정상 표시되면서 본문이 읽히면 통과. 붙지 못하면 고정이 걸린 것 — 중단.

산출 — 복호화 성공 여부 (실패 시 5번 대체 방안으로)

제스처별 캡처

복호화가 되면, 각 동작을 하나씩 따로 일으키고 그때 나간 요청에 라벨을 붙인다. 이렇게 해야 어떤 요청이 무엇인지 확실해진다:

  • 전투력 랭킹 화면 진입
  • 서버(월드) 변경
  • 다음 페이지 / 스크롤
  • 전체 서버 조회 ↔ 개별 서버 조회 전환
  • 특정 캐릭터 눌러 상세정보 열기
산출 — 제스처 ↔ 요청 매핑

구조 기록

각 요청을 아래 3번 양식에 옮긴다. 특히 URL·메서드·본문 필드와 응답 필드, 그리고 인증 헤더의 위치·형식을 빠짐없이.

산출 — 요청/응답 구조 문서

자동화 판정

기록을 4번 기준에 대입해 GO / NO-GO 를 가른다. GO 여도 그 다음에야 코드를 쓴다.

산출 — 자동 수집 가능 여부 결론
✕중단 관문 — 인증서 고정이 확인되면 여기서 멈춘다
P3 에서 CA 를 신뢰 저장소에 넣었는데도 클라이언트가 연결 실패·네트워크 오류를 낸다면, 앱이 자기 인증서만 신뢰하도록 고정한 것이다. 이걸 넘어서는 유일한 길은 고정 로직을 무력화하는 것 — 보안 기능 우회이고, 이 조사가 명시적으로 배제한 영역이다. 이 경우 조사를 종료하고 5번 대체 방안으로 간다.
판정 테스트 — CA 활성 상태에서 게임이 ① 평소처럼 로그인·랭킹 표시되면 통과 / ② 접속·통신 오류를 내면 고정 있음 → 중단

라이브 관찰 1회 — 이 케이스 전용

단 하나를 가른다: 랭킹 읽기가 세션만으로 되나, 요청마다 서명이 필요한가

정적 분석은 여기서 멈췄습니다. 이 절차는 본인 계정 트래픽을 한 번 관찰하고, 내가 만든 요청을 몇 번 재전송해 서버가 무엇을 강제하는지 봅니다. 재전송 ≠ 서명 위조 — 내 요청을 그대로 다시 보내거나, 서명 헤더를 빼거나, 본문만 바꾸고 서명은 안 건드리는 것은 관찰입니다. 새 유효 서명을 계산하는 것만이 위조이고 그건 하지 않습니다.

준비 — 수집 전용 계정 · 공식 클라이언트 · mitmproxy

전용 계정으로 공식 PC 클라이언트에 로그인. mitmproxy 설치. 게임 버전 기록. 지역이 스카니아면 대상 호스트는 makr-service.nexon.com.

복호화 프록시 세우기

mitmproxy CA 를 Windows 신뢰 저장소에 넣고 시스템 프록시를 mitmproxy 로. mitmweb 에서 필터 ~d makr-service.nexon.com. (.NET 클라이언트라 SSLKEYLOGFILE 은 안 먹을 확률이 높아 이 경로로 간다.)

인증서 고정 관문 — 여기서 갈린다

프록시+CA 켠 상태로 로그인 → 전투력 랭킹 진입. 정상 연결·표시되면 통과. 연결 실패·인증서 오류면 고정이 걸린 것 — 즉시 중단(고정 우회는 금지선). 이 경우 결론은 "관찰 불가 → 공식 클라이언트 필요".

랭킹 요청 1건 포착

전투력 랭킹을 열고 한 번 스크롤(2페이지=cursor 도 같이 잡히게). mitmweb 에서 랭킹 서비스로 가는 요청을 찾아 기록:

  • 경로 · 메서드 · HTTP/2 여부
  • 요청 헤더 — 인증 토큰 헤더와, 서명/nonce 헤더(x-signature·x-nonce·x-toy·x-gssdk 류)
  • 본문(MemoryPack 바이너리 — 디코딩 없이 바이트째로 다뤄도 됨)
  • 응답 상태·크기·랭킹 행 포함 여부
=결정 테스트 — 재전송 3종 (위조 없음)
mitmproxy 의 replay 또는 포착한 헤더/본문으로 내 요청을 다시 보낸다. 각 테스트 결과가 답이다.
T1 · 그대로 재전송 (토큰·서명·본문 전부 원본)
200+동일 데이터 → 재전송 성립 / 401·서명오류 → nonce 1회성·시간종속 = 요청 서명 강제 신호
T2 · 서명만 제거 (인증 토큰은 유지, 서명/nonce 헤더 삭제)
200 → 세션 토큰만으로 충분 → 전용 계정 세션 수집 가능 / 401·서명필요 → 서명 강제
T3 · cursor만 변경, 서명은 원본 유지 (다음 페이지로 본문만 수정)
200+2페이지 → 본문이 서명에 안 묶임 = 세션으로 페이지네이션 가능 / 본문·서명 불일치 오류 → 본문이 서명에 묶임 → 클라이언트 필요
※ T3 는 서명을 다시 계산하지 않는다. 원본 서명을 그대로 두고 서버가 거부하는지만 본다 — 위조 아님.

자동 수집 가능 여부 판단 기준

범위(본인 계정 · 우회 없음) 안에서 되는지를 가른다

핵심 질문 하나: “본인이 정상 로그인으로 얻은 토큰만으로, 화면에 보이는 공개 랭킹을 페이지 넘겨가며 읽을 수 있는가?” 이게 되면 GO, 각 요청이 클라이언트에 묶인 서명을 요구하면 NO-GO.

count/limit/pageSize 로 지정, cursor 로 전체 열람 구조 — 상위만이 아님. 서버 상한값은 라이브 1회 필요
6 캐릭터 프로필
RankerInfo 행 + 동일 서명 API 계열. 인증·서명 뒤
7 클라이언트 전용
사실상 예 — 요청마다 세션키+롤링 nonce 서명(GSSDK·무결성검사·NxLog). 클라이언트만 유효 요청 생성
?결론 — 추가 자료 필요 (라이브 관찰 1회)
정적 분석은 여기까지가 끝이고, "불가능"에 부딪히지 않았습니다. 클라이언트에는 GetBattlePowerRankingList(cursor·worldId·filterType 페이징) → GetGuildMemberList · SearchNick 로 characterId 확장 → GetBriefUserInfoList(공개 프로필·외형) 까지, 발견-누적형 자체 DB 를 만들 API 구성요소가 정상 기능으로 실재합니다. 인증은 본인 전용 계정의 정상 로그인(NpToken→GameToken→SessionKey)으로 재현 가능합니다.
남은 단 하나의 질문 — 이 호출들이 유효 세션만으로 되는가, 아니면 요청마다 클라이언트가 만드는 서명을 요구하는가. 서명 인프라(SessionKey·NextSignatureNonce·GSSDK)는 존재하지만, 랭킹 읽기 호출에 그것이 강제되는지는 정적 문자열로 확정 못 합니다. 본인 계정 라이브 관찰 1회로 갈립니다: 세션만으로 되면 전용 계정 세션 수집 가능, 서명 필요면 공식 클라이언트 실행 필요. 그 전엔 어느 쪽도 단정하지 않습니다.
GO — 범위 안에서 가능
  • P3 복호화 통과 (고정 없음)
  • 랭킹이 Bearer 토큰 하나로 읽힌다 — 본인 로그인으로 얻은 그 토큰
  • 토큰 만료·갱신 방식이 관찰되어 재현 가능
  • 페이지네이션이 파라미터화됨 (page/cursor/limit 를 내가 바꿔 넣을 수 있다)
  • 본문을 바꿔 재요청해도 서명 거부가 없다
NO-GO — 범위 안에서는 불가
  • 인증서 고정으로 P3 자체가 막힘
  • 요청마다 본문+nonce+시각 HMAC 서명이 붙고, 그 키가 클라이언트에 박혀 있다 → 재현하려면 서명 로직을 뜯어야 함(우회)
  • 토큰이 실시간 기기/세션 하트비트에 종속 — 클라이언트가 살아 있어야만 유효
  • 응답이 TLS 안에서 다시 암호화된 불투명 블롭
경계는 “내 토큰으로 공개 데이터를 읽기”와 “클라이언트의 서명·인증을 재현하기” 사이에 있습니다. 앞은 내 세션으로 열려 있는 걸 읽는 것 — 범위 안. 뒤는 보안 기능을 복제하는 것 — 범위 밖. 토큰 만료 시 본인이 다시 로그인해 갱신하는 건 유지비일 뿐 우회가 아닙니다.

별도 검토

범위 재확인 — 이 프로토콜은 본인 PC 클라이언트가 본인 계정으로 정상 표시하는 트래픽만 관찰합니다. 인증서 고정·암호화·인증·기타 보안 기능의 우회는 어느 단계에서도 하지 않으며, P3 관문에서 고정이 확인되면 조사를 종료합니다.

참고 — 랭킹은 게임 안에서 누구나 보는 공개 정보입니다. 반면 넥슨 오픈 API 약관 8.15 는 authorized use 밖의 자동 질의·크롤링을 제한합니다. GO 로 판정돼 구현으로 넘어가기 전에, 수집 규모·주기·재배포 방식이 이용약관과 어긋나지 않는지 별도로 확인하십시오. 이 문서는 기술 절차서이며 법률 자문이 아닙니다.
